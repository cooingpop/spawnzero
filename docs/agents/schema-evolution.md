# Schema Evolution

이미 저장된 데이터를 깨지 않으면서 스키마를 넓히고 줄이는 규칙.

**적용 범위**: 저장된 데이터가 있는 모든 것 — 관계형 DB, 모바일 로컬 DB,
JSON 문서 저장소, 파일 포맷, 외부에 나가는 API 응답. 스택과 무관하다.

**언제 읽나**: 컬럼·필드·테이블을 추가·변경·삭제하기 **전에**. 마이그레이션
파일을 쓰기 시작한 뒤가 아니라 쓰기 전이다.

## 왜 규칙이 필요한가

기능을 더할 때 스키마를 고치는 것은 피할 수 없다. 문제는 **이미 저장된 행과
이미 배포된 코드가 그 변경을 모른다**는 것이다. 사고는 항상 같은 모양이다.

1. 컬럼을 지웠는데 아직 옛 코드가 돌고 있어서 `column does not exist`가 난다
2. `not null` 컬럼을 default 없이 추가해서 기존 행이 전부 위반이 된다
3. 컬럼 이름을 바꿨는데 되돌릴 방법이 없다 — 옛 이름의 데이터는 이미 없다
4. 타입을 바꿨는데 변환이 안 되는 값이 섞여 있어서 마이그레이션이 중간에 멈춘다

넷 다 "배포 순간에는 코드와 스키마가 반드시 어긋난다"는 사실에서 나온다.
**코드와 스키마는 절대 동시에 바뀌지 않는다.** 배포는 순차적이고, 롤백은
코드만 되돌린다.

## 하드 룰

| 금지 | 왜 | 대신 |
| --- | --- | --- |
| 컬럼·필드 **삭제** | 아직 그 컬럼을 읽는 코드가 돌고 있다. 롤백하면 확실히 돈다 | 먼저 안 쓰게 만들고, **다음 릴리스에서** 지운다 (아래 3단계) |
| 컬럼·필드 **이름 변경** | 삭제 + 추가와 같다. 옛 이름의 데이터가 사라진다 | 새 컬럼 추가 → 양쪽 쓰기 → 복사 → 옛 컬럼 제거 |
| **타입 변경** | 변환 불가능한 값 하나에 마이그레이션 전체가 멈춘다 | 새 컬럼 추가 → 변환하며 복사 → 전환 |
| `not null` 컬럼을 **default 없이** 추가 | 기존 행이 전부 위반이라 추가 자체가 실패한다 | nullable로 추가 → 백필 → `set not null` |
| 제약을 **바로 유효화** | 큰 테이블을 잠그고, 기존 위반 행 하나에 실패한다 | `not valid`로 추가 → 고친 뒤 `validate` |
| 이미 적용된 마이그레이션 **수정** | 적용한 환경과 안 한 환경의 스키마가 영원히 달라진다 | 새 마이그레이션을 하나 더 만든다 |

**하나만 기억한다면: 넓히는 것은 즉시, 줄이는 것은 두 릴리스 뒤.**

## 확장-축소 3단계 (Expand / Migrate / Contract)

되돌릴 수 없는 변경을, 각 단계가 되돌릴 수 있는 세 조각으로 나눈다.

```
1. Expand    스키마를 넓힌다. 옛 코드도 새 코드도 둘 다 돈다.
             새 컬럼은 nullable이거나 default가 있다. 아무것도 지우지 않는다.
             → 여기서 배포해도 안전하고, 롤백해도 안전하다.

2. Migrate   데이터를 옮기고, 코드가 새 자리를 쓰게 한다.
             한동안 양쪽에 쓴다(dual write). 읽기는 새 자리를 먼저 본다.
             → 옛 자리가 아직 살아 있으므로 롤백이 여전히 된다.

3. Contract  아무도 옛 자리를 읽지도 쓰지도 않는 것이 확인된 뒤에 지운다.
             **확인은 코드 검색이 아니라 관측이다** — 로그·메트릭으로
             접근이 0인 것을 본다.
```

3단계는 **최소 한 릴리스 뒤**다. 같은 배포에 1·3단계를 같이 넣으면 3단계를
나눈 의미가 없다.

## 넓히는 쪽의 기본값

- **새 컬럼은 nullable로 시작한다.** 값을 백필한 뒤에 `not null`을 건다.
  세 문장으로 나눠 쓴다: `add column` → `update ... where ... is null` →
  `alter column ... set not null`.
- **새 컬럼은 기존 코드가 몰라도 되어야 한다.** 기존 `insert`가 그 컬럼을
  쓰지 않고도 성공해야 한다(default 또는 nullable 또는 트리거).
- **새 테이블·새 열거값 추가는 안전하다.** 단, 열거값을 **제거**하는 것은
  삭제와 같다.
- **`select *` 를 쓰지 않는다.** 컬럼이 늘 때마다 모든 질의가 무거워지고,
  컬럼이 줄 때 어디가 깨지는지 알 수 없다.

## 줄이는 쪽의 절차

컬럼을 정말 없애야 할 때:

1. 코드에서 **읽기**를 먼저 없앤다. 쓰기는 남겨 둔다. 배포한다.
2. **쓰기**를 없앤다. 컬럼은 그대로 둔다. 배포한다.
3. 관측으로 접근 0을 확인한다.
4. 마이그레이션으로 지운다.

급하다고 1·4를 한 배포에 합치지 않는다. 합치는 순간 롤백이 불가능해진다.

## 파괴적 변경을 사람에게 올린다

다음은 에이전트가 **임의로 실행하지 않는다.** 계획과 영향 범위를 적어
사람에게 확인받는다.

- 컬럼·테이블 삭제, 이름 변경, 타입 변경
- 데이터를 지우거나 덮어쓰는 `update` / `delete`
- 이미 적용된 마이그레이션의 수정
- 큰 테이블을 오래 잠그는 작업 (인덱스 재작성, 테이블 재작성)

## 마이그레이션 파일의 규칙

- **한 파일은 한 번만 적용돼도, 두 번 적용돼도 같은 결과여야 한다.**
  (`if not exists`, `create or replace`, 조건부 백필.) 적용 여부를 사람이
  기억에 의존해 추적하는 상황이 반드시 생긴다.
- **이미 적용된 파일은 고치지 않는다.** 고쳐야 하면 새 파일을 만든다.
- **되돌리는 방법을 파일 안에 적는다.** 적을 수 없다면 그 변경은 3단계로
  나눠야 한다는 신호다.
- **번호는 순차**로 하고, 순서대로 실행하면 빈 DB에서 현재 스키마가 나와야
  한다.

## 검증

규칙은 지켜지는지 확인할 수 있어야 규칙이다. 프로젝트에 맞게 하나 이상을
둔다.

- **금지 구문 검사**: 마이그레이션 파일에서 `drop column`, `rename column`,
  `alter column ... type`, `drop table`을 찾아 실패시키는 스크립트. 의도된
  축소는 명시적 주석으로 예외 처리한다.
- **빈 DB에서 전체 재생 테스트**: 마이그레이션을 순서대로 돌려 현재 스키마와
  일치하는지 본다.
- **과거 데이터 보존 테스트**: 옛 버전 형태의 행을 넣고 마이그레이션을 돌린
  뒤, 그 행이 **그대로 있는지** 확인한다. 스키마 일치만 보면 데이터가 사라진
  것을 놓친다.
- **타입 생성 동기화 검사**: 스키마에서 타입을 생성한다면, 마이그레이션만
  들어가고 타입 재생성이 빠진 커밋을 CI가 잡게 한다.
